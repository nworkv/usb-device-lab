# Подключение checkpoint к кампаниям dashboard

Этот этап заменяет backend стандартного supervisor кампанией с checkpoint.
Прежняя точка запуска сохраняется:

```sh
python -m usb_device_lab.dashboard serve --config lab.toml --port 8765
```

«Запустить» создаёт новую логическую кампанию и начальный checkpoint. «Остановить»
завершает текущую попытку; checkpoint фиксируется после Store.finish. «Возобновить»
восстанавливает PRNG и продолжает оставшийся бюджет той же логической кампании.
Технический ID сессии supervisor остаётся новым, campaign_id из checkpoint сохраняется.
Счётчик runs в состоянии supervisor отражает глобальный прогресс, не только попытки
после последнего resume. JSON supervisor-state и события сохраняются прежними классами.

Файл results_dir/campaign-checkpoint.json отдельный от supervisor-state.json.
В runs.sqlite3 добавляется campaign_attempts(campaign_id, iteration, run_id).
Запись mapping фиксируется после Store.begin, до execute. Параметры и compatibility
проверяются через checkpoint.py. Identity — hash полей конфигурации, кроме параметров
кампании, которые проверяются отдельно. Engine hash включает локальные исходники
цикла, checkpoint, выбора/мутаций, модели, runner/storage/agent. Изменение этих файлов
или полной версии Python требует новой кампании; не обновляйте код во время работы.
Удалённая версия host-кода этим hash не подтверждается: оператор должен обеспечить
совместимый host agent. SSH/USB и фактические тайминги не становятся детерминированными.

Перед resume читаются и проверяются digest содержимого всех индексированных файлов
корпуса, в порядке Store.corpus. Используется bounded/no-follow читатель CorpusBrowser:
до 4096 элементов и 256 КиБ на конфигурацию. Новые seeds при resume не вносятся.
Перед каждым выбором родитель читается тем же безопасным читателем. Manifest всё ещё
проверяется start/resume стандартным supervisor. Новая кампания восстанавливает
старые running-запуски через прежний Store.recover и сохраняет их историю.

## Fail-closed вместо молчаливого повторения

Resume отвергается ДО execute и HostOrchestrator, если обнаружено:

- отсутствие checkpoint/БД, несовместимый runtime/engine/identity/параметры;
- изменение или повреждение файлов корпуса;
- любой незавершённый running-запуск;
- отсутствие/неполная последовательность campaign_attempts;
- несовпадение количества завершённых попыток или last_run с checkpoint;
- последняя попытка с FATAL-диагностикой;
- уже исчерпанный бюджет.

JSON и SQLite не одна транзакция. Если Store.finish успел закоммитить результат,
а checkpoint не сохранился, фиксируется DB/checkpoint gap. Этот этап НЕ чинит gap,
НЕ повторяет незавершённую попытку и НЕ откатывает БД автоматически. Изучите артефакты,
проверьте стенд и явно начните новую кампанию. Не редактируйте tracking/checkpoint,
чтобы принудительно обойти проверку. Ошибка записи checkpoint прекращает цикл.
Блокировка campaign.lock берётся до проверок/оркестрации и удерживается до cleanup.
Она не даёт глобальной эксклюзивности UDC между разными каталогами результатов.

HTTP 202 означает принятие асинхронной команды. Отказ проверки checkpoint позже
виден как failed/error в supervisor; не все несовместимости дают синхронный 409.
Для старых сессий без checkpoint автоматического fallback на новую кампанию нет.
Начните новую кампанию кнопкой «Запустить».

## Совместимость

Прямой lab/runner CLI fuzz остаётся без записи checkpoint; обновлён dashboard backend.
Не запускайте старый CLI одновременно с управляемой кампанией. Custom backend из
трёх аргументов остаётся поддержанным, но не получает checkpoint-resume автоматически.
Старые документы первого этапа описывают прежнее состояние до этого подключения.

```sh
python -m unittest discover -s tests -p 'test_checkpoint_*.py'
```

12 новых целевых тестов прошли при подготовке: stop/resume сравнивается с непрерывным
циклом, проверяются бюджет, смена engine, повреждение корпуса, pending-run, gap без
нового покрытия, отсутствие файлов, preflight, lock, FATAL и передача resume/progress
через реальный изменённый CampaignSupervisor. Использована логика checkpoint.py
и реальные файловые операции/SQLite; Store, DeviceConfig, Mutator, CorpusBrowser,
preflight и host/executor были подставными. Checkpoint-код восстановлен из предыдущего
коммита в изолированном пакете; полный checkout не использовался. Старые 17 codec-тестов,
полный набор репозитория, наследники persistent/event, браузер, SSH/KCOV и физический
стенд в этом прогоне не проверены. Нельзя считать этот прогон готовностью стенда.

База подготовки: feature/kernel-triage, c15a92eb15261d211ef5bfe439ca8e8d1a31702a.
control.py сверен с Git blob 973f64c1b0fff1569b10f164ab2a00a07a971799.
Полный patch на реальном checkout здесь не прогонялся. В ZIP есть полные новые/
изменённые Python-файлы и отдельный panel-ui-integration.patch только для подсказки.
Используйте ZIP с этим UI patch либо общий patch, не оба варианта поверх друг друга.
